# 1. The verdict, in one page

**The code is not the problem. The process the code faithfully encodes is the problem.**

This is well-built software. In three days of looking for broken wiring I found **zero dead buttons, zero method mismatches, zero response-shape mismatches, and zero reachable SQL injection**. Every one of the 84 client calls resolves to a real endpoint. XSS escaping in `pd.html` is thorough. The file-upload guards are real. The candidate-screen arithmetic is mathematically correct — I re-derived it independently and it agrees to the paisa. The prose in the app is unusually good; the verdict explanations in `screen_candidate` are better-written than most commercial software.

What you have built is a **faithful port of a six-gate, ten-role, twenty-surface corporate stage-gate system**. `pd-lib.js` says so in its own header: *"intentionally faithful to that source rather than 'improved'."* That was the right decision for the port. It is the wrong system for the team that has to use it.

**The arithmetic of the adoption problem** (counts traced through the code, **CODE** not **LIVE** — I did not walk one idea end to end through the browser, so treat the action and field counts as accurate to within a step or two, not to the unit):

| | |
|---|---|
| Human actions to take ONE idea from submitted to launched | **16** (22 on the path My Work actually steers you down) |
| Distinct screens involved | **7** (10) |
| Distinct people who must act | **6** |
| Form fields across that journey | **~95** (~140) |
| Menu items shown to a QC Head / RTA / Production / Agronomy | **19** |
| Menu items shown to the COO | **21** |
| Write actions available to Agronomy | **4** — every one of which the Custodian already has |
| Write actions available to Production | **5** |
| Write actions available to CEO, Consultant, Team member | **0** |
| Fields on the "share a half-formed idea" form | **12** (only 2 are actually required — nothing says so) |

You are asking a small R&D team to operate a governance apparatus sized for a company with a full-time PMO. That is why nobody inputs anything. It is not a UI polish problem, and no amount of button-tidying fixes it.

**The second problem, and it is worse than the adoption problem:** the gates are not actually enforced. I proved live that an idea can be pushed from *"just submitted, never screened"* straight to *"validated, hand to Production"* in **one API call**, and that a **completely blank Development Record** — 28 of its 42 columns empty — can pass RTA technical review, the Custodian completeness check and G2 design approval in three calls with empty bodies, after which its fields lock forever. The app's own screen says *"The rule this form enforces: no sample is made until Sections 1–3 are written."* That rule is not enforced.

So the situation is: **the process is too heavy to follow, and simultaneously light enough to walk around.** People will discover the second fact quickly, and then the record becomes theatre.

# 2. What is genuinely good (do not break these)

Worth naming, because the fix list below is long and it would be easy to conclude the thing is rotten. It is not.

1. **The `screen_candidate` arithmetic engine** (`pd-lib.js:188-225`). Pure, testable, correct. `exworks = (rm + conversion)/(1 − loss)`; `cost_per_kg_p = exworks/(10p)`. I hand-checked the unit reasoning — 1 tonne at *p*% P₂O₅ is `10p` kg — it is right. Thresholds are right, no off-by-ones, division-by-zero guarded, negative loss clamped. **LIVE**
2. **The written explanations.** `'N 4.10% is below the target minimum of 6.00%. The farmer buys the shortfall as urea; that cost sits in the parity model, not here.'` That is how software should talk. There is more of this in PD than in most products I see.
3. **The provisional / placeholder discipline.** Every price and assay carries a *basis*, and a placeholder can never quietly pass as procurement data. This is a genuinely good idea and rare.
4. **Wiring integrity.** No dead buttons, no orphan features reachable by accident, correct route ordering in `server.js` (PD API at :518 → assets :523 → launcher :525 → `/pd/drop` :527 → `/pd` :529 → O2S catch-all :531). **LIVE**
5. **XSS discipline in `pd.html`.** `esc()` at `:164` covers `& < > " '`, and every user-supplied string reaching `innerHTML` is wrapped. My Work labels are pre-escaped server-side and the code says so.
6. **The auto-audit middleware** (`server.js:292`) — one capture point instead of per-handler calls. Right architecture, incomplete coverage (see §4.9).
7. **The visual design.** The screenshots are clean, calm, well-spaced, consistent. The sidebar, typography and colour are good. **This is not a visual problem.**

# 3. The diagnosis — why nobody puts anything in

You asked specifically why people don't input data, problems, products, ideas, formulations, tests. Here is the causal chain, each link evidenced.

### 3.1 The lowest-friction door is invisible to everyone who would use it

`/pd/drop` is a **4-field, no-login page** — name, contact, source, "the idea or problem". It is the single best-designed intake surface you have and takes 45 seconds.

The **only** link to it anywhere in the codebase is at `pd.html:1452`, inside the Drop-box triage screen — which requires the `dropbox` surface, granted only to COO and Custodian (`pd-lib.js:134`). `launcher.html` does not link it. The PD home page does not link it. The Guide does not mention it. **CODE**

> The one door built for people who don't have accounts is advertised only to the two people who have full access.

### 3.2 The idea form looks like a twelve-question exam and reads like one

12 fields, eight of them **numbered 1–8**. Server-side only `title`, `idea_text` and `change_type` are required (`pd-routes.js:30`). There is not a single `required` attribute or asterisk in the entire app — so the form *looks* like twelve obligations. **LIVE** (screenshot attached)

Questions 3, 5 and 8 — *"Why might it work?"*, *"How would we know it worked?"*, *"Any risk or worry you already see?"* — ask a lab technician with a half-formed idea for information that only exists **after** screening. The page's own intro says *"a good question is enough"* and then presents eight questions.

### 3.3 There is no draft, no autosave, and the app's own advice destroys your draft

Zero occurrences of `localStorage` draft-saving, autosave, or `beforeunload` anywhere (`pd.html`, `drop.html`). Close the tab, take a call, hit refresh — twelve fields gone. **CODE**

Worse: the similar-idea checker injects an amber panel at `pd.html:384`, *between the title field and question 1*, with each match rendered as `<a href="#idea/N">`. Clicking it fires the hash router, which replaces `main` — **following the app's own "check before submitting" instruction wipes the half-written idea with no warning and no way back.** **CODE**

### 3.4 The similar-idea check greets people with the word KILLED

It fires at **six characters** of combined title+text, debounced 500 ms, and renders in an amber `⚠` card. On six characters of a MySQL natural-language match, false positives are the norm. The message a first-time submitter is most likely to see is *"Killed before — reason: …"*. The counterweight — *"Still different? Submit anyway"* — is grey subtext at the bottom of a warning box. **CODE / LIVE** (I confirmed the endpoint returns exactly this shape.)

### 3.5 Every error message is one line at the bottom of a long form

`pd.html:415` writes `"Title and the idea itself are required."` into `#f_msg` — which sits *below all twelve fields*, next to Submit. No field highlighting, no focus, no scroll, no indication of which of the two is missing. Same pattern on Problem, Challenge, and the drop box (whose message renders *above* the form). **CODE**

Typed data is preserved on failure. That part is fine.

### 3.6 Operators land on "You are all caught up" when they are not

My Work is the landing page for 7 of 10 roles. On day one, with an empty database, everyone lands on a green panel reading *"You are all caught up. Nothing is waiting on you."* next to a 19-item menu. **LIVE** (screenshot attached)

For two roles it is permanently misleading:

- **Agronomy** has exactly **one** My Work query (`pd-routes.js:252`) — ideas at stage `field_trial` with no trial row. Once the trial is designed, My Work says "caught up" for the entire growing season. No sowing prompt, no observation prompt, no harvest prompt.
- **Production** has **two** sections, both grey and non-actionable, and its one "take to launch" link points at `#formulations`, where `pd-routes.js:1072` forbids Production from writing anything. **CODE**

### 3.7 G3, G4, G5 and G6 appear in nobody's queue

The four committee gates that gate the entire back half of the pipeline are in **no role's My Work** (`pd-routes.js:219-261`). The "Next step" banner that would prompt them exists on exactly **one screen** — the idea detail page (`pd.html:548`). To record a gate, somebody must independently remember to open the Gate log and find the idea in a dropdown of every live idea in the company. **CODE**

> This is where the pipeline stalls silently. Nothing is broken, nothing errors — the work simply never surfaces, and the sample, test, trial and launch downstream of it stay frozen.

### 3.8 Roles that can read everything and do almost nothing

`qc_head`, `rta`, `production` and `agronomy` share one branch in `allowed_surfaces()` (`pd-lib.js:135-136`) — **identical read access, all 17 surfaces**. An agronomist is handed a 19-item menu to perform four actions, all four of which the Custodian already holds. **LIVE** (nav counts confirmed in a real browser: COO 21, agronomy 19, lab_tech 9, member 4)

### 3.9 On a fresh route, every candidate is amber BORDERLINE and nobody can tell why

`pd_route_screens.cost_ceiling_per_tonne` defaults to `0`, and `pd-lib.js:206` warns whenever the ceiling is 0. Any warning at all downgrades the verdict from `pass` to `borderline` (`pd-lib.js:220`). Meanwhile every one of the 10 seeded materials is placeholder-priced, so every candidate is also flagged provisional.

I ran it: **a perfect recipe with real assay and invoice data still returns `borderline` on a fresh route.** A green PASS is unreachable out of the box. To get one, someone must first fill 10 bar values and replace 50 material values. **LIVE**

### 3.10 The verdict enum is shown raw, and so are ~24 other database values

`BORDERLINE` is printed as an uppercased raw enum with no legend and no explanation of what to do about it (`pd.html:979`). The same pattern appears in ~24 places: `heavy` / `light` instead of "Heavy lane", `field_trial`, `being_addressed`, `bench_done`, `qc_head`, `na`, `superseded`, and the Activity log's path-derived slugs (`ideas_screen`, `records_pre`, `POST /api/pd/records/12/pre`).

**`pd-lib.js` already defines every human label needed** — `STAGES`, `PD_ROLES`, `GATES`, `LANES`, `PROJECT_STATUS`. The app simply doesn't use them in these places. This is the cheapest large improvement available. **CODE**

### 3.11 The person granting roles sees raw database keys

The launcher's Access grid — the one screen where a human picks somebody's PD role — renders `Object.keys(PD_ROLES)`, not the labels. The COO's dropdown literally reads:

> `coo, ceo, qc_head, rta, production, agronomy, custodian, member, lab_tech, consultant`

No labels, no descriptions. `server.js:391` sends `PD_ROLE_KEYS`; `launcher.html:354` prints `esc(o)`. **CODE**

**RTA is never expanded anywhere in the system.** I grepped `pd.html`, `pd-lib.js`, `launcher.html`, `ARCHITECTURE.md`, `PORTING_STATUS.md` — every occurrence is the bare abbreviation. An employee cannot learn what it stands for from this software.

### 3.12 There is no way to find an idea by its number

H-numbers are displayed everywhere and are not searchable. There is no search on Ideas, Board, Records, Samples or the Gate log. `#idea/N` is keyed on the **database id**, not the H-number, so knowing "H-042" does not let you type a URL. The only fulltext lookup in the app is the similar-idea hint buried inside the new-idea form. **CODE**

### 3.13 Not usable on a phone

One media query in the whole app (`pd.html:98-107`), and it only restyles the sidebar. At ≤760px the four nav group headings are **hidden** (`.navgrp{display:none}`), leaving 21 undifferentiated links wrapping across the top. Inputs are 13px — below iOS Safari's 16px threshold, so every field tap zooms the page. Buttons are ~33px tall against a 44px touch guideline. **Zero `type="number"` and zero `inputmode` in the entire app** — every numeric field shows the alphabetic keyboard. **CODE**

# 4. Correctness, integrity and security

Severity ordered. Everything marked **LIVE** I executed against your running code.

### 4.1 🔴 CRITICAL — Gate order is not enforced. One call takes an unscreened idea to "validated"

`pd-routes.js:421-440` validates the gate name, the decision word, the reason string and that the hypothesis exists. It validates **nothing** about the idea's stage or its prior gates. Then:

```js
if (decision === 'advance' && pd.GATE_ADVANCE_STAGE[gate])
  await pdq('UPDATE pd_hypotheses SET stage=? WHERE id=?', [pd.GATE_ADVANCE_STAGE[gate], hid]);
```

**LIVE reproduction.** Submitted a brand-new idea, then one call:

```
POST /api/pd/gates/decide  {hypothesis_id:1, gate:"G6", decision:"advance", reason:"skipping every gate"}
→ {"ok":true,"provisional":false}
```

Database afterwards:

```
h_number  stage       screen_decision   change_type  lane
1         validated   (empty)           new          heavy

pd_gate_decisions: 1 row total — G6 / advance
```

Never screened. No G1, G2, G3, G4 or G5 row exists. It is now `validated` and appears in Production's "take to costing, registration and launch" queue. This is available to `rta`, `custodian` and `coo`, and there is no uniqueness constraint — the same gate can be decided repeatedly with contradictory outcomes.

This one route contradicts the whole rest of the app. G2 checks its preconditions, records check `screen_decision='log'`, samples check for a G3 advance. G3–G6 check nothing.

### 4.2 🔴 CRITICAL — A blank Development Record passes RTA review, completeness and G2, then locks forever

`POST /records/:id/pre` (`pd-routes.js:333-350`) and `/post` (`:398-414`) have **zero emptiness checks**. The client has none either. `/complete` (`:367-376`) stamps a timestamp with no content validation whatsoever.

**LIVE reproduction.** Created a record and wrote nothing. Three empty-body calls:

```
POST /records/1/rta-review  {}  → {"ok":true}
POST /records/1/complete    {}  → {"ok":true}
POST /records/1/g2          {}  → {"ok":true,"delegated":false}
```

Result: `record_no DR-0001`, `status approved`, `g2_signed 1`, **28 of 42 columns NULL or empty**, and a `G2 / advance / "Design approved: DR-0001"` row written to the gate log.

Then, trying to fill in the design afterwards:

```
POST /records/1/pre {"problem_statement":"the real design"}
→ "Sections 1–3 are locked — the design was already approved at G2. A changed design is a NEW record."
```

So the blank record is now permanent and unfixable. Meanwhile `pd.html:631` tells the user: *"The rule this form enforces: no sample is made until Sections 1–3 are written."*

Compounding it: the record disappears from the QC Head's My Work the instant it is created (`pd-routes.js:195` uses `NOT EXISTS … pd_dev_records`), while simultaneously appearing in the RTA's review queue (`:196`, `WHERE review_rta_at IS NULL`, no content filter). **The system's own queues push a blank record toward approval.**

### 4.3 🔴 CRITICAL — Every 403 leaves the screen stuck on "Loading…" forever

`route()` (`pd.html:276-314`) wraps its dispatch in `try/catch`, but every branch is `return renderX(hash)` — a promise returned out of the `try` without `await`. **The catch block is unreachable dead code.** I proved the JS semantics independently. 27 of the 29 `render*` functions have no `try/catch` of their own; each opens with `shell('… Loading…')` then `await api(...)`.

**LIVE reproduction.** Signed in as `lab` (`pd_role=lab_tech`) and navigated to screens outside that role's surfaces:

```
#records    → "Development Records  Loading…"     (forever)
#trials     → "Field trials  Loading…"            (forever)
#gatelog    → "Gate log  Loading…"                (forever)
#problems   → "Problem register  Loading…"        (forever)
#audit      → "Activity log  Loading…"            (forever)
```

The server sent a perfectly good message every time — *"Not permitted: records. Your PD role: lab_tech. Ask the COO or Data Custodian for access."* — and it went to the browser console where no user will ever see it. Every 403, 500, and network drop looks identical to a hung server.

Related: the **only** 401 handler in the file is at `pd.html:1694`, inside `boot()`. Once the app has started, an expired or invalidated token produces the same permanent "Loading…". And `server.js:31` falls back to a random per-process `SESSION_SECRET` when the env var is unset — **every deploy or restart then invalidates every token**, and nobody gets sent back to the login screen. *Confirm `SESSION_SECRET` is set in Render before go-live.*

Also: any unrecognised hash silently renders Home rather than a "not found" (`pd.html:310`). **LIVE** — `#nonsense-typo` rendered the Home page.

### 4.4 🔴 CRITICAL — `/api/login` has no rate limit, no lockout, no delay, and eight accounts share one seeded password

`server.js:311`. `grep` for `rateLimit|lockout|attempts` across `server.js` and `pd-routes.js` returns **zero matches**. The only rate limit in the codebase is 5/hour on the public drop box.

**LIVE reproduction.** 30 rapid wrong-password POSTs to `/api/login` — **30/30 accepted, no throttle, no lockout, no delay.**

`DEFAULT_USERS` (`server.js:34-43`) seeds eight accounts all with password `van@2026`, usernames `admin`, `kam`, `lab`, `cfo`, `plant`, `production`, `qa`, `supply`. `admin` is the COO, and `runPdMigration` (`server.js:233`) automatically grants `admin` the `coo` PD role. On my fresh instance `admin`/`van@2026` logged straight in. **Whether your live database still holds those passwords I cannot see from here — check it today.** The absence of throttling is confirmed regardless.

Secondary, same line: `verifyPw` runs only when the user exists, so a nonexistent username returns instantly while a real one costs a `scryptSync` — a username-enumeration timing oracle, and (because `scryptSync` blocks the event loop) a single-request DoS vector.

```
ORDER BY calc_cost_per_kg_p ASC puts the ZERO-PHOSPHORUS candidate FIRST
```

`target_p2o5_min` defaults to `0`, so a zero-P candidate is not a FAIL, is therefore selectable, and then tops `candsToMake` (which has no verdict filter). The QC Head's and Lab Tech's make-queue is headed by the candidate containing no phosphorus. Use `NULL` and sort last.

### 4.14 🟡 MEDIUM — Custodian "tracker update" is a whole-row overwrite that silently resets omitted fields

`pd-routes.js:1411-1420`. `const stage = pd.STAGES[b.stage] ? b.stage : 'proposed';` — **a PUT that omits `stage` resets the idea to `proposed`.** Omitting `priority` or `next_action` blanks them. This is a full overwrite disguised as a partial update. It also lets a Custodian set `stage='validated'` directly with no gate row and no reason — a second, quieter bypass of §4.1.

Same pattern at `:788` (trials — omitting `status` reverts a `harvested` trial to `designed`), `:901` (projects — reopens a closed project, blanks all four brief fields), `:1005` (regulatory), `:968` (product link — unlinks the problem).

### 4.15 🟡 MEDIUM — `launcher.html`'s `esc()` does not escape apostrophes, and is used inside a JS string in an HTML attribute

```
launcher.html:266   .replace(/[&<>"]/g, ...)          ← no '
pd/pd.html:164      .replace(/[&<>"']/g, ...)         ← correct
```

`launcher.html:354` builds `onchange="__setmod('` + esc(username) + `', ...)"`. A username containing `'` breaks out of the JS string in every admin's browser. `POST /api/platform/users` blocks it with a regex (`server.js:446`), but the legacy `POST /api/users` (`:486`) and `PUT /api/users/:username` (`:495`) apply **no** username validation. One-character fix. Reachability **INFERRED** — I did not exercise it end to end.

### 4.16 🟡 MEDIUM — Screen-bar targets accept negative and out-of-range values, poisoning every candidate on a route

`pd-routes.js:645`: `const f = k => Number(b[k]) || 0;` — no clamping. `target_p2o5_max: -5` makes every candidate warn forever (verdict can never be `pass`); `target_p2o5_min: 999` makes every candidate FAIL, which blocks selection entirely. Contrast `POST /api/pd/materials` at `:568`, which clamps correctly — the settings route just didn't get the same treatment.

### 4.17 🟢 LOW (but note them)

- **Enum allow-lists are `obj[userInput]` truthiness checks** and inherit `Object.prototype`. Verified by execution: `LIB_TYPES['constructor']`, `STAGES['constructor']`, `PD_ROLES['constructor']` are all truthy. A file named `payload.constructor` passes the upload extension allow-list. Impact is contained (randomised filename, never served statically, octet-stream fallback) — an allow-list bypass, not RCE. Fix once, everywhere: `Object.prototype.hasOwnProperty.call(TABLE, key)`.
- **Library files sit on ephemeral disk.** `PD_LIBRARY_DIR` defaults to a path inside the app directory. On Render that is wiped on every deploy unless it points at a mounted persistent disk. The DB row survives, the file does not. `libTotalBytes()` is displayed but **never enforced** — no quota. `fs.writeFileSync` blocks the event loop on every upload.
- **The drop box honeypot silently discards on autofill.** `pd-routes.js:1485` returns `{ok:true}` and stores nothing if the hidden field named "Website" is non-empty. It is a real `<input type=text>`; any password manager or accessibility tool that fills it causes the submission to vanish **while showing the user the full success message**. No logging, no trace.
- **The drop box's 15-character minimum is undisclosed** until a server round-trip. There is no client-side validation on that page at all.
- **The drop box rate limit is per-IP, 5/hour.** On a shared office NAT that throttles the whole company to 5 submissions an hour.
- **`express.json({limit:'25mb'})` applies to the public drop box** — an unauthenticated caller can force 25MB of body buffering per request; the rate limit is applied *after* the body is parsed.
- **No confirmation dialog exists anywhere.** `grep "confirm("` in `pd.html` → **zero matches**. G1 KILL, G3–G6 KILL, "Approve design (G2)" (which permanently locks 16 fields), "Make this — log a sample", drop-box dismiss: none confirm, none undo. The only reversal in the system is the COO's 7-day light-lane veto.
- **`PUT /api/pd/users/:username/role`** (`pd-routes.js:1537`) is an orphan — no client calls it — and writes only `auth_users.pd_role`, never `user_module_roles`. If anyone ever wires it up, the two diverge: the user gets PD access but the launcher tile stays locked; or loses PD access while the tile stays unlocked and the COO's own Access screen lies to them. **Delete it.**
- **Trial codes use `COUNT(*)+1`, not `MAX+1`** (`:755`). Delete any `FT-2026-xx` row and the counter collides permanently.
- **LIKE wildcards unescaped** (`:1021`, `:1181`) — searching `%` matches everything. Cosmetic.
- **`CONFLICT_MIN_PCT = 1.0`** means zinc sulphate at a realistic 0.5% dose falls below the "trace" cut-off and its recorded incompatibilities are silently skipped. Domain call, but 1% is high for a micronutrient.
- **`k2o_pct` exists in the schema and is ignored by `screen_candidate`.** No potash in the seed today, so latent.

### Two arithmetic questions for you, not bugs

1. `conversion_cost_per_tonne` is grossed up by `1/(1−loss)` along with raw materials. That is correct **only if** conversion cost is quoted per tonne of *input*. If it is per tonne of *output* — the more common convention — the loss is double-counted. The comment says this matches your cost-parity workbook; worth one check against that sheet.
2. The field is named `cost_per_kg_p` but computes cost per kg **P₂O₅**. Anyone reading it as elemental P is wrong by 2.29×. Rename it `cost_per_kg_p2o5`.

### Things I checked and found clean

No reachable SQL injection anywhere — I enumerated all 9 `next_number` call sites (all hardcoded literals), the `IN (...)` builders (placeholders only), and the fulltext searches (parameterised, natural-language mode). No user-controlled `ORDER BY`, `LIMIT` or column name exists in the codebase. `lane` cannot be set by the client. `is_admin` cannot be injected via any body. Negative recipe percentages cannot be stored (silently filtered at `:662`). The path-traversal guard on the file route is real, auth genuinely runs before the file is streamed, and all five claimed upload guards exist. Token signing uses HMAC-SHA256 with `timingSafeEqual`, expires at 30 days, and the secret fallback is random-per-process, not hardcoded. Route order in `server.js` is correct. `pd.html` has no `<script src=>` and nothing fetches `pd-lib.js` from the browser.

One real weakness in the auth model: **there is no token revocation of any kind.** Changing a compromised user's password does not invalidate their token, and revoking a COO's access does not strip the `r:'COO'` claim already baked into it — that ex-COO keeps platform admin for up to 30 days. Note that `pdAuth` deliberately reloads `pd_role` fresh from the DB *"so a role change takes effect immediately"* (`server.js:268`); the platform side never got that treatment.

## 6.3 The strategic question — and my honest read

You said: *"we have to make a sample or we have to run a strategic r&d. i want a single platform."*

Those are two different products, and PD today is trying to be the second while your team needs the first.

- **"Run strategic R&D"** is what PD models: six gates, a committee, a delegated-authority scheme with ratification, a portfolio of concepts judged on gates A–E, a doctrine page. This apparatus makes sense when you have a dozen concurrent programmes, a real R&D budget under scrutiny, and an audit trail that a board or a regulator will read. It is a governance system.
- **"Make a sample"** is what a small fertilizer R&D team does most days: someone has an idea, someone screens a recipe on paper, someone makes it in a beaker, someone tests it, someone writes down what happened. That needs a lab notebook with a memory, not a stage-gate.

You built the governance system first, faithfully, and it works. But governance without volume is overhead — you have **zero ideas in the system** and a sixteen-step approval pipeline waiting for them. The order is backwards. Nobody adopts a governance system before there is anything to govern.

**My recommendation, and I'd hold it loosely because you know your organisation and I don't:**

**Ship a subset tomorrow, not the whole thing.** Turn off — by hiding the nav items, which is a `NAV` array edit, not a rewrite — everything except:

> **Home · Ideas · Board · Samples · Lab tests · Library · Guide**, plus **My Work** for the two or three people who actually run the bench.

That is 7–8 menu items instead of 21. It is the lab notebook. It covers "somebody had an idea", "we made it", "we tested it", "here's what we know". No gates, no records, no candidates, no portfolio, no formulation register.

Then run G1 screening **in a weekly meeting off a printed Board**, and have the Custodian type the decision in afterwards. One person doing data entry for a team of ten is a completely respectable way to start, and it is how every successful internal system I've seen actually got its first hundred rows.

**Turn the rest on one gate at a time**, each when there is real work waiting for it: G2 records when the first idea is genuinely worth designing; the candidate screen when the first route needs costing; trials when there is something to sow. Each of those is already built and tested — you are not throwing anything away, you are sequencing it.

The single platform you want is not at risk from this. It is the same codebase, the same login, the same launcher tile. You are only choosing what is visible on day one.

**And do the four-hour list first regardless of which path you pick.** A team that discovers on week two that a blank record can pass G2, or that one API call can mark an unscreened idea "validated", will never trust the gates again — and at that point the adoption problem becomes unfixable by design changes.
